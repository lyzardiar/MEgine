# Scene 交互查询性能评估

Author: MiYu

当前交付保留 `bef555a` 的引擎实现与 Release。实验读取器通过逐项验证对象 ID、父节点和限制集合来复用 Scene 查询快照；局部查询耗时降低，但整体渲染、模拟推进没有通过性能验收，因此实验源码已恢复，默认 QA 构建 EXE 也恢复为已验收版本。

成功运行顺序为旧、新、新重复、旧重复、新版无 App 断点。另一次计数探针初始化错误在移动及 Play 采样前退出，不计入比较；原报告保留。查询计数探针只用于两次标注为 candidate 的运行，条件始终 false，并在移动测量前移除。无 App 断点运行未设置该探针；仍执行相同面板切换。真实 Footman 点击验证使用的 math3d 条件断点在所有版本相同阶段设置并移除。

无 App 断点新版与前一次旧版比较：查询调用栈采样耗时下降 49.62%，Scene 绘制耗时增加 16.66%。相邻旧版分别约6.83与6.90 ms，三个新版约7.76、8.08与8.05 ms。移除新增 App 探针没有恢复整体表现，不能将差异只归因于该探针。局部 CPU 优化不等于用户体验改善，也未证明缓存逻辑是整体回退的唯一原因；该实验未交付。

采样期间没有构建或 CPU 测试。同一 Frostbound Main.js、相同交互和画面大小；查询耗时按实际加载模块的 TypeScript AST 函数范围归属，包含查询读取器、原查询及内部函数，嵌套调用不重复累计。完整 JSON 保留函数范围及采样时长。Game 全区间包含采样启停和桥接读取，固定10秒从首个绘制时间加1秒开始并保留停顿。观察到 MuMu 与 Cursor 同时占用 CPU，无法据此证明运行间差异的因果关系；未停止用户应用。

实验17项针对性测试、前端与 Release 构建通过，覆盖层级编辑/撤销/重载、Play 动态对象、同长度替换、集合变化、重复 ID、循环、缺失父节点、旧批次独立和9,000节点逐项验证。五次成功运行 Edit/Play 移动空画面均为0；等待相机拾取、父子变换/激活、真实模型点击、原生显隐像素 oracle、UI/粒子、相机预览和层级滚动通过。六次自有 QA 进程退出，隔离 Main.js 恢复并核对哈希，临时材质/meta移除。实验源码恢复后已重建前端，已交付的游戏 Main.js 保持原哈希。
