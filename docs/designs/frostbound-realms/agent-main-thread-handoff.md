# 大场景编辑器响应

Author: MiYu

当前发布的 Warcraft 场景包含 48,127 个实体。层级面板逐行调用 `store.sceneVisible` 和 `store.scenePickable`，这两个函数通过 `list().find` 沿父级查询。空限制集合下仍然遍历实体数组，使完整层级刷新产生大量重复查找并占用前端主线程。

限制集合为空时，状态查询直接返回允许值。存在限制时保留原来的父级检查，包括隐藏父级下新创建的子对象和运行模式中的检查；隐藏与选中限制仍只属于编辑器状态。

原生请求携带本机接收时间；调用方可通过 `traceTiming` 获取前端接收、处理完成、FIFO 排队和操作耗时。普通 RPC 返回结构保持原样；计时不会缓存到重复写命令的结果中。`qa-agent-native-timing.mjs` 在隔离工程上测量当前发布脚本和场景。可选的 CPU 采样只连接该次 QA 专用端口中的 WebView。

2026-10-08 原生前后对照均通过，场景与 Main 脚本哈希相同，初始化之后的测量命令序列相同：

| 对局状态下的操作 | 样本数 | 修改前中位耗时 | 修改后中位耗时 |
| --- | ---: | ---: | ---: |
| 输入命令 | 3 | 7,557.42 ms | 1,331.31 ms |
| 状态查询 | 4 | 193.37 ms | 129.59 ms |
| 单步执行 | 3 | 903.83 ms | 1,036.77 ms |

输入往返中位耗时减少约 82.4%。基线中一次输入的 7,557 ms 包含约 7,550 ms 的前端投递等待，操作本身低于 1 ms、写队列等待为零。CPU 采样将热点关联到层级行渲染中的 `sceneVisible`、`scenePickable` 和实体数组查找。基线绘制样本的前端 paint 为约 101 ms，原生 render 为约 51 ms；它们不能解释接近 8 秒的帧间隔。

源码算法基准中，两次状态查询遍历全部 48,127 行，中位耗时从 9,681.79 ms 降到 2.13 ms。该测量仅覆盖 Node 中的状态查询，不能当作整个编辑器或游戏的加速比。原生表格也只覆盖该场景及这组暂停输入、查询、单步序列；样本数有限，未测试物理输入、音频和完整验收流程的总耗时。

前端/协议测试 20 项、桥接与场景集成测试 32 项、层级状态测试 6 项和 Rust 桥接测试 22 项通过。TypeScript、前端构建及原生 Release 构建通过。三次原生验收均无控制台错误，实例正常退出，隔离工程与存档清理完成。验证指纹和命令见 `agent-main-thread-validation.json`。

源码变更只涉及编辑器状态查询与诊断桥接；游戏 Main、场景和 asset-library 均未修改。原生 Release 构建分别耗时 5 分 19 秒与 4 分 30 秒，属于本次交付成本，未作为性能基准。

后续定位从约 1 秒的单步执行继续，分别测量运行时步进、快照导出、桥接刷新和 React 提交。非空隐藏或选中限制集合仍使用原有祖先查询，需要另行验证并优化。完整 Warcraft III 战役、原版编辑器行为、经典地图及跨机器联机的完整复刻仍未完成。
