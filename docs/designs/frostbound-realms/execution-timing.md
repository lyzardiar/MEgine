# 原生验收耗时与优化顺序

Author: MiYu

2026-10-08。数据来自 `native-warden-qa.json` 与 `native-warden-textures-qa.json` 的命令计时，只覆盖两次守望者原生验收，不代表整个开发任务耗时。

玩法验收四阶段累计 731.234 秒。按命令类型汇总：

| 操作 | 次数 | 累计秒 | 占四阶段耗时 | 中位数秒 |
| --- | ---: | ---: | ---: | ---: |
| 输入 playback.input | 57 | 333.089 | 45.6% | 9.129 |
| 状态查询 entity.get | 34 | 171.539 | 23.5% | 9.134 |
| 单步 playback.step | 58 | 96.711 | 13.2% | 1.141 |
| 截图 view.screenshot | 5 | 49.469 | 6.8% | 9.930 |

工程打开及就绪阶段为 88.075 秒；它与上述命令统计重叠，不能再次相加。输入、查询和单步合计占约 82.3%。当前场景包含 48,127 个实体。

纹理验收两阶段累计 326.830 秒，其中工程就绪为 80.106 秒、四技能及存档恢复为 246.724 秒。18 次输入累计 60.460 秒，10 次查询累计 69.454 秒，23 次单步累计 87.359 秒，4 次截图累计 35.403 秒。输入释放已与后续命令合并；两次验收覆盖范围和操作数量不同，不能把总耗时之比当作性能提升。

已确认的开销是大型场景中的串行命令往返、重复状态查询、单步等待、截图及工程初始化。输入桥接已省去两个全场景快照；独立暂停桥接基准由 311.964 毫秒降至 0.022 毫秒，但该测量不包含外部排队、原生执行、渲染与 IPC，不能解释当前秒级往返。端到端计时还不能区分这些环节的占比。

优化顺序：

1. 记录请求接收、前端开始及结束、原生开始及结束、绘制完成和响应发送的时间，使用同一请求编号关联。
2. 将连续输入和单步组成保持顺序的批次，在业务断言边界读取状态，减少往返次数。
3. 在工程及产物指纹一致且运行状态可恢复时复用验收实例；必要的冷启动验证单独执行。
4. 以源码及资产哈希确定重新生成与回归范围；通过的检查仅在相关改动或新风险出现时重跑。
5. 资产转换后先检查全部材质与特效引用，再做原生画面验收；当前 `.mfx` 引用检查已覆盖此前漏检的 16 处纹理路径。

当前纹理验收通过，实例正常退出，隔离工程及存档已清理。下一项性能定位应使用同一场景和同一命令序列，先拆分耗时再修改瓶颈。

## 主线程定位与复测

2026-10-08 已补充本机接收、前端接收、操作和 FIFO 排队计时，并完成 CPU 采样。热点来自层级面板对每行重复执行的 Scene 可见性与选中限制查询。空限制集合的查询现在直接返回允许值。

同一发布场景、Main 脚本和命令序列下，3 次输入的往返中位耗时从 7,557.42 ms 降至 1,331.31 ms，减少约 82.4%；3 次单步中位耗时为 903.83 ms 与 1,036.77 ms，未改善。完整范围、源码基准、测试和下一项瓶颈见 `agent-main-thread-handoff.md` 与 `agent-main-thread-validation.json`。这些结果不是四技能完整验收或整个游戏的加速比。
