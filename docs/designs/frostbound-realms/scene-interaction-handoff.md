# Warcraft editor Scene interaction

Author: MiYu

The published Warcraft scene contains 52,709 entities. With any Scene visibility or picking restriction, hierarchy rows and Scene viewport filtering previously performed an entity-array search at every ancestor. A refresh could therefore repeat billions of comparisons even when only one object was restricted.

`sceneInteractionQuery()` captures the current entity-parent numbers and both restriction sets for one query batch. Iterative ancestor resolution memoizes inherited state within that batch, including cyclic and missing-parent data. Empty restrictions inspect no entities. Hierarchy rows and App render filtering use fresh batches; marquee selection creates its batch when the event begins. Viewport live picking and single-click guards retain their current-runtime queries because completed Play frames can change between panel renders.

The Agent bridge exposes `view.set_scene_visibility` with `{id, visible}` and `view.set_scene_pickability` with `{id, pickable}`. Both accept only existing entities in Edit mode and invoke the same editor-only store methods as the UI. They have discoverable parameter schemas and return the effective inherited state. Scene content, Undo history and Play worlds are not modified by these commands. These are bridge commands; no named MCP tool wrapper was added.

`benchmark-scene-interaction.mjs` compares both existing scalar interfaces against a freshly constructed batch over all 52,709 visible rows with one hidden and one unpickable root. It verifies identical results for every row. Three measured samples have median durations of 5,550.452 ms before and 39.383 ms after, including batch index construction. This is a Node query benchmark, not editor FPS, physical input latency or a native end-to-end speedup. The scene and source fingerprints are recorded in `scene-interaction-benchmark.json`.

Eight final query tests cover independent flags, native generational identifiers, immutable snapshots, cycles, missing parents, a 60,000-level chain, creation, reparenting, Undo, reload, remote state, Play additions, 52,709-entity read counts, command guards and actual Hierarchy component rendering. Existing command/schema tests and AgentBridge, hierarchy and Play regressions are also exercised. Native command acceptance uses `qa-scene-interaction.mjs` and the complete published scene with three empty fixture entities. It resolves live identifiers by exact entity name and verifies the child-parent relationship before commands, because native scene loading maps file identifiers to generational entity handles. The report records command timing, editor/source fingerprints, Scene state checks and a paused native-input start of the actual skirmish. It does not validate physical picking or viewport pixel visibility.

An initial attempt to inspect the entire native window exceeded the bridge query timeout before any restrictions were applied. Its failed report is preserved as `native-scene-interaction-ui-timeout.json`; it is not a comparable native baseline. The instance was later confirmed absent, while its disposable fixture remains at `E:/work/codex/cache/mengine/native-qa/scene-interaction-1791474563942`. No user-owned editor was closed. Full-window semantic collection is a separate unresolved performance path.

Vite resolves its root from the configuration file's canonical directory, so frontend builds use the same path when launched through either workspace alias. Native Release builds require `tauri/custom-protocol` to embed the frontend; without it, Tauri's context generator uses the configured development URL and embeds no frontend assets. The native verification executable is built with `cargo build -p mengine-editor-tauri --release --features tauri/custom-protocol --target-dir D:/MEngineNativeQA/construction-build`. A startup attempt without that feature is preserved in `native-scene-interaction-startup-timeout.json`; it is not an accepted native build.

Further work includes live hit-test queries, large hidden-ID filters and full-window semantic snapshots. Complete Warcraft III faction behavior, campaigns, classic TD/Dota content, physical input, audio and cross-machine LAN fidelity remain unfinished. The full recreation goal remains active.

Native acceptance passed on the published scene with inherited restrictions: all three selection/query cycles, branch clearing, unchanged authored-scene state and the actual F1 skirmish start completed. The first paused Play step took 3,481 ms; the second took 2,921 ms. Console errors were zero. The owned editor exited normally and its disposable fixture and QA storage were removed. `native-scene-interaction-qa.json` records the current successful run. The QA script focuses Game View and uses the established native execution timeouts for Play verification; Scene interaction measurements happen before this switch. This verifies the final path, without assigning the earlier timeout to a specific runtime cause.

`scene-interaction-timing.json` separates local query cost, native request dispatch/handler timings and build costs. The traced commands in the earlier failed Play run spent 47,001 ms between native receipt and frontend dispatch out of 63,239 ms total; handler time was 13,899 ms. This establishes a scheduling/wait boundary, not its underlying cause. The accepted Release build took 262 seconds. Configuration rework took an additional 385 seconds. The earlier Play timeout and runtime-ID failure remain recorded in `native-scene-interaction-play-timeout.json` and `native-scene-interaction-id-qa.json`; none is treated as a passing run. `scene-interaction-validation.json` ties the accepted checks to file fingerprints and their exact scope.
